An **adapter** translates Paginate's request for a count and a slice of records into the operations supported by your database or API. You only write one yourself if your data source does not already have an integration.

## Choose the integration for your project

| Your data source | Package | Pagination modes | What you provide |
| --- | --- | --- | --- |
| **Drizzle ORM** | [`@evensurface/paginate-drizzle`](/docs/adapters/drizzle) | Page, offset, cursor | A Drizzle query factory; a count query for page/offset. |
| **Better Auth** | [`@evensurface/paginate-better-auth`](/docs/adapters/better-auth) | Page, offset | Better Auth's database `adapter`, a model name, and optional filters. |
| **Other ORM, API, or array** | [`@evensurface/paginate`](/docs/adapters/create-your-own) | Page, offset, cursor | A small custom adapter following the relevant core interface. |

## Drizzle example

```ts
import { asc } from "drizzle-orm"
import { paginate } from "@evensurface/paginate-drizzle"
import { db } from "./db"
import { users } from "./schema"

const result = await paginate({
  query: () => db.select().from(users).orderBy(asc(users.id)),
  countQuery: db.$count(users),
  page: 2,
  limit: 10,
})
```

The Drizzle wrapper executes `countQuery` and applies limit/offset to the select built by your query factory. Its returned item types are inferred from Drizzle. Start with the [Quick Start](/docs/getting-started/quick-start) or [Drizzle ORM Adapter](/docs/adapters/drizzle).

## Better Auth example

```ts
import { paginate } from "@evensurface/paginate-better-auth"

const result = await paginate<{ id: string }>({
  adapter: ctx.context.adapter,
  model: "user",
  select: ["id"],
  sortBy: { field: "id", direction: "asc" },
  page: 2,
  limit: 10,
})
```

`ctx.context.adapter` belongs to your **server-side Better Auth plugin endpoint**. The wrapper calls Better Auth's `count()` and `findMany()` internally. Better Auth model names are strings, so the caller supplies an explicit item type when precise typing is needed. Enforce authorization and tenant filters in the endpoint. See [Better Auth Adapter](/docs/adapters/better-auth) for joins, input validation, and compatibility requirements.

## What happens inside a page request?

For **35 matching records** and `page: 2, limit: 10`, Paginate:

1. Normalizes the requested page and limit.
2. Counts matching primary records (`35`).
3. Calculates `offset = (2 - 1) × 10 = 10`.
4. Fetches at most `10` records starting after the first `10` matches.
5. Returns `items` plus metadata such as `total: 35`, `totalPages: 4`, and `hasNextPage: true`.

Drizzle and Better Auth run these operations through different database APIs. Both count and fetch separately; concurrent changes can make the results reflect different snapshots.

## When should I write a custom adapter?

If your source is not Drizzle or Better Auth, implement the framework-independent core contract:

```ts
interface PaginationAdapter<TQuery, TCountQuery, TItem> {
  count(query: TCountQuery): Promise<number>
  fetch(
    query: TQuery,
    options: { limit: number; offset: number },
  ): Promise<TItem[]>
}
```

`count()` returns the number of matching records. `fetch()` returns up to `limit` rows after skipping `offset`. See [`PaginationAdapter`](/docs/api-reference/types#paginationadapter) and [Create Your Own Adapter](/docs/adapters/create-your-own).

**Cursor pagination uses a different interface**: `fetch(query, { position, limit })` and `getPosition(item)`, with no count. It is available in the Drizzle integration or through a custom core adapter, **not through the Better Auth wrapper**. See [Cursor Pagination](/docs/guides/cursor-pagination).
